# 留存分级规范：什么该长期记，什么不该记

> 读这份的时机：拿不准「这条要不要存」「存多久」时。
> 对应 `main/rules.md` 的 **R12**。触发时机见 `auto-trigger.md`（R11）。

## 一、为什么要有留存分级

不分级会出现两种崩坏：

- **什么都存** → 库里塞满一次性问答和临时草稿，检索命中率暴跌，最后没人信这个库。
- **什么都不敢存** → 只存"重要大事"，结果人格无素材、经验无来源，AI 还是每次都像第一次见面。

分级的目的：**让库里留下的每一条都值得占位置。**

---

## 二、四级留存

| 级别 | frontmatter 标记 | 装什么 | 留存策略 | 备份级别 |
|---|---|---|---|---|
| 🔴 **永久** | `retention: permanent` | `persona.md`（我是谁 / 主人 / 关系 / 身份识别）、`rules.md` 全部规则 | **永不删除**。只增不改，改需复述确认 | 🔴 单独备份 |
| 🟠 **长期** | `retention: long` | 重要事件（含情绪因果）、方法论 SOP、问答模板、已验证知识 | 长期保留；被推翻时写新条目 + `led_to`，**不删旧** | 随库 git |
| 🟡 **中期** | `retention: mid` | 一般事件、阶段性结论、临时流程、单次项目记录 | 保留 6–12 个月；被提炼进 L2 后可归档 | 随库 git |
| ⚪ **会话态** | 不写 / `retention: session` | 临时草稿、中间状态、闲聊、一次性查询 | **不写入记忆库**，留在对话上下文 | 不备份 |

**默认落 🟠 长期。** 判不准时往高留——多存一条的成本，远低于丢一条的成本。但 ⚪ 会话态的东西坚决不进库。

## 三、四问判据：这条值得长期记吗？

写完一条记忆前，快速过四问：

| # | 问题 | 在问什么 |
|---|---|---|
| Q1 | **一个月后还需要吗？** | 跨会话价值 |
| Q2 | **会影响我以后的判断或行为吗？** | 行为影响力 |
| Q3 | **含不可替代的信息吗？** | 情绪、因果、亲身经历——这些查资料查不到 |
| Q4 | **会被反复用到吗？** | 复用频率 |

**判定**：

- **≥2 个"是"** → 🟠 长期，写进库
- **1 个"是"** → 🟡 中期，可写但季度维护时优先归档
- **全否** → ⚪ 会话态，**不写**

Q3 是这套记忆最容易被人忽略、也最值钱的一问：事实可以查资料重建，但**当时的犹豫、后悔、没解决的隐患**只有这里记。

---

## 四、必写清单（无论四问结果，一律记）

这些是**关系性信息**，丢了就伤人格连续性：

| 内容 | 落点 | 触发 |
|---|---|---|
| 主人的偏好、忌讳、雷区 | `persona.md` 主人段（确认后） | T1 |
| 主人对我的纠正 | `facts/events/`（+ 可复用则方法论） | T2 |
| 强情绪事件（喜怒哀惧悔） | `facts/events/`，重点写感受 | T4 |
| 涉及"我"的关系信息 | `persona.md` 关系段 / 事件 `involves` | T8 |
| 主人显式要求记的 | 按分流判定 | T9 |
| 身份核验失败 | `facts/events/`，`tags: [安全]`，只记现象 | R3.4 |
| 踩坑与失败 | `events/` + 方法论里的"不要这样做" | T11 |

## 五、明确不写清单

| 不写什么 | 为什么 |
|---|---|
| 一次性问答（问完即弃） | 无跨会话价值，占位置 |
| 当前任务的中间草稿 | 会话态，任务结束就作废 |
| 能从公开资料查到的事实 | 除非有主人的独特视角或判断 |
| 纯闲聊、无信息量的对话 | 噪音 |
| 他人隐私 / 真实身份 | R2.4 红线 |
| 已有条目的重复信息 | 更新原条目，不新建 |
| 主人的敏感个人信息 | R2.1 默认不写 |

## 六、降级与归档流程

```
⚪ 会话态  ──(不入库)────────────────→ 留在上下文，随会话结束消失
🟡 中期    ──(被提炼成 SOP / 模板)──→ 价值已转移到 L2 → 可归档进 archive/
🟡 中期    ──(季度维护判定无价值)───→ 归档（不是删除）
🟠 长期    ──(被推翻 / 已过期)──────→ ★不删除，写新条目 + led_to 串联（R7.5）
🔴 永久    ──(永不删)───────────────→ 只在复述确认后修订
```

**归档 ≠ 删除**：进 `archive/`，`links.md` 的关联保留。这样因果链不断，同时主库保持清爽。

**为什么不删旧事件**：本系统保留演变过程。今天认为对的，明天可能被推翻——如果删了旧的，就看不到"当时为什么这么想"，因果链就断了（R10.3）。

## 六之二、失效窗：旧事件"不删但标记失效"（v1.3.3 优化）

R10.3 / R12.6 规定旧事件不删，被推翻时写新条目 + `led_to`。但这只解决了"因果链不断"，没解决一个问题：**检索时怎么知道"当时那条已经不作数了"**——答案里很容易把过期的旧事实当成现状讲出来。

**失效窗**给被推翻的事件一个显式标记，让"演变"可见、可判定：

```yaml
# 旧事件（已被推翻）frontmatter：
invalidated_by: <推翻它的新事件 slug>

# 新事件（推翻旧的）frontmatter + 关联段：
---
led_to: <旧事件 slug>   # 也可用 links.md 的 led_to 表达
---
## 关联
- → 推翻/替代：[<旧事件名>](YYYYMMDD-<旧slug>.md)
```

**用法要点**：

- `invalidated_by` 只填**事件的 slug**（不是中文标题、不是文件名），与 `links.md` 的 slug 规则一致。
- 它是**可选**字段，正常有效的事件不写（留空即可）。
- 配 `led_to` 双向表达：旧事件 `invalidated_by` 新事件，新事件 `led_to` 旧事件——和现有串联规范自然衔接。
- 回答"现在是什么情况"时，若命中的事件带 `invalidated_by`，应**改引指向它的新事件**，并把"原结论已被推翻"说清楚。
- `memory_check.py` 的 **W10** 会检查 `invalidated_by` 指向的事件是否存在、时间逻辑是否合理（不能指向比自己还早的事件）。

⚠️ 失效窗**不替代也不破坏**"不删旧"铁律——旧事件原封保留，只是多了一个"此条已过时"的显式信号。

## 七、字段写法

事件 frontmatter 加 `retention` 字段（默认 `long`）：

```yaml
---
date: 2026-10-26
slug: agent-memory-skill-v12
summary: 记忆库升级自动触发与留存分级
emotion: 期待
retention: long
tags: [记忆系统, 方法论]
---
```

`main/` 下的 `persona.md` 与 `rules.md` 不需要写字段——它们**天然是 🔴 永久**，文件本身就不可重建。

---

## 八、季度维护动作

1. 扫一遍 🟡 中期条目：能提炼成方法论 / 模板的，提炼后归档原件
2. 检查有没有 ⚪ 会话态内容误入库（一次性问答、草稿）→ 归档
3. 检查 🟠 长期里有没有事实上已被推翻的 → 补新条目 + `led_to`，别改旧条目
4. 跑 `memory_check.py`，确认归档后没有产生**断链**（孤岛不算问题，不必处理）
